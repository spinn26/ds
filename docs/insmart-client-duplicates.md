# Дубли клиентов из Insmart: почему так вышло

**Дата разбора:** 11–12.08.2026
**Коммиты:** `9493fe90`, `a6932194`, `a17fd6b7` (все на проде)

---

## Коротко

Вебхук Insmart на каждый оплаченный полис ищет клиента в базе и, если не нашёл,
заводит новую карточку. Проверка по телефону в коде **была**, но по факту почти
никогда не срабатывала — из-за формата номера и логики выбора кандидата. В итоге
на одного человека заводилась вторая карточка, и его контракты расползались по
двум клиентам.

Починили три вещи: нормализацию телефона, выбор кандидата и регистр почты.
Плюс — защиту от обратной ошибки: приклеить полис к чужой карточке.

---

## Как работал поиск клиента

Схема legacy-шная и это половина проблемы:

| Таблица  | Что хранит |
|----------|------------|
| `person` | реального человека: ФИО, **почта, телефон**, ДР |
| `client` | карточку клиента у конкретного партнёра: `client.person` → FK, `client.consultant` → чей клиент |

У `client` своих контактов почти нет — почта и телефон лежат в `person`. Значит,
поиск «есть ли уже такой клиент» — это всегда два шага: найти `person` по
контакту → найти живую карточку `client` на этом `person`.

Старый код ([InsmartIntegrationService.php](../app/Services/InsmartIntegrationService.php)) делал так:

```php
$personId = person.where('email', $email)->value('id');        // 1) по почте
if (!$personId) $personId = person.where('phone', $phone)->value('id');  // 2) по телефону
if ($personId) { ... client.where('person', $personId)->first() }        // 3) карточка
// не нашли → создаём person + client
```

Логика правильная. Ломалось исполнение.

## Четыре причины сбоя

### 1. Телефон сравнивался как строка

В базе один и тот же номер лежит во всех видах сразу:

```
+7 904 390 46 79
+79043904679
79043904679
89043904679
```

Так вышло потому, что номера попадают в базу из разных источников с разными
правилами: вебхук Insmart, импорт контрактов из Google Sheets, ручное заведение
в кабинете, историческая заливка из Directual. Никто из них не приводил номер к
одному виду, и валидации формата на входе нет.

`where('phone', '+7 904 390 46 79')` не находит строку `79043904679` — для SQL это
разные значения. Проверка по телефону молча возвращала «не найдено» и код шёл
создавать нового клиента.

**Канон сверки теперь — последние 10 цифр** ([Phone.php](../app/Support/Phone.php)).
Именно 10, а не все цифры: `7904…` и `8904…` — один и тот же российский номер с
разными префиксами, и по казахстанским (`7707…` / `8707…`) правило работает так же.
Меньше 10 цифр — не сверяем вообще, обрывок вроде `12345` склеил бы разных людей.

### 2. Брали первого попавшегося `person`

`->value('id')` возвращает **одну** запись — по сути произвольную. А у человека с
двумя почтами в базе лежат **два** `person` на один телефон.

Дальше происходило вот что: код брал «первый» `person`, у него живой карточки не
было, и вместо того чтобы посмотреть остальных кандидатов — шёл создавать третьего.
Ровно тот случай, с которого начался разбор: разные почты, один телефон, дубль.

Теперь собираем **всех** кандидатов (по почте + по телефону) и ищем живую карточку
среди них. Если карточек несколько — предпочитаем карточку текущего партнёра, чтобы
не утащить клиента в чужую ветку.

### 3. Почта сравнивалась регистрозависимо

`K@yandex.ru` и `k@yandex.ru` — для PostgreSQL разные строки, для почтового сервера
один ящик. Такие пары в базе есть. Теперь `lower(btrim(email))`.

Это та же грабля, что уже ловили на логинах партнёров (см. заметку про
регистрозависимый вход по email) — просто в другом месте.

### 4. Обратная ошибка: полис на чужую карточку

Когда сверку по телефону починили, вылезла противоположная опасность. **Один номер
телефона — это не один человек.** Данные говорят прямо:

```
79055140601 → Прядко Наталья Леонидовна   (nlp0601@gmail.com)
             Прядко Людмила Николаевна    (priadko_nata@mail.ru)
             Черкасова Бэлла Анатольевна  (nlp0601@gmail.com)

79122318321 → Башегурова Регина Равильевна (reginabashegurova@gmail.com)
             Иванова Анна Михайловна       (Reginaproinvest@gmail.com)
```

Это семья и клиенты агента, который вписывает свой телефон в полисы родни — та же
картина, что уже разбирали в кейсе ложной самопокупки. Если матчить только по
номеру, полис дочери прикрепится к карточке матери.

Поэтому карточку по телефону переиспользуем, **только если совпало ФИО
застрахованного** (или карточка принадлежит текущему партнёру — у своего клиента
могла смениться фамилия). Почта считается сильным признаком и такой проверки не
требует.

Отдельно есть **drift привязок**: одна запись `person` держит карточки разных людей
(наследство переномерации `person` при консолидации Directual — `client.person`
тогда не обновляли). Из-за него мало найти живую карточку на нужном `person` —
надо ещё убедиться, что это тот человек. Та же проверка по ФИО закрывает и это.

## Что исправлено

| Коммит | Что |
|---|---|
| `9493fe90` | [InsmartIntegrationService](../app/Services/InsmartIntegrationService.php): нормализация телефона, все кандидаты вместо первого, регистронезависимая почта, дозапись пустого телефона найденному `person`; та же нормализация в детекторе самопокупки |
| `a6932194` | [AdminDataController](../app/Http/Controllers/Api/AdminDataController.php): страница «Дубли клиентов» (`by=phone`) группировала по всем цифрам — `7904…` и `8904…` были разными группами. Тот же канон: 229 групп → 239 |
| `a17fd6b7` | Защита от обратной ошибки: карточка по телефону берётся только при совпадении ФИО застрахованного либо если она принадлежит текущему партнёру |

Новый `App\Support\Phone` держит канон в одном месте — и для PHP, и для SQL, чтобы
следующая проверка телефона не разошлась с этой.

## Что осталось

- **Слияние 7 настоящих дублей** — через существующую страницу «Дубли клиентов»
  (`/admin`, режим «по телефону», кнопка объединения). Для трёх межпартнёрских
  нужно решение, чья карточка остаётся.
- **158 групп drift привязок** — это отдельная задача про `client.person`, к Insmart
  отношения не имеет. Команда `clients:realign-person` чинит только однозначные
  случаи (на проде их 7); остальные 935 без совпадения ФИО и 226 неоднозначных
  требуют ручного разбора.
- **Нормализация телефона на входе** — сейчас канон применяется при сверке, но в
  базу номер по-прежнему пишется как пришёл. Привести формат при сохранении
  (кабинет, импорт, вебхуки) — снимет причину, а не следствие.
